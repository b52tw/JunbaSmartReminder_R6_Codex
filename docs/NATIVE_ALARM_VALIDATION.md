# 原廠鬧鐘建立與核對

本輪以 Android 公開 `ACTION_SET_ALARM` 介面改善送出流程。開啟的是手機能處理此介面的時鐘 App，不能保證一定由 vivo 原廠時鐘接收，也不能讀取原廠完整清單、確認儲存結果或控制原廠貪睡次數。

## 行為

- 手動建立可選不重複、每日、每週。每週沿用所選「下一次時間」的星期；需要其他星期或多個星期時，請在原廠時鐘調整。
- 送出前顯示預計下一次的日期、時間、時區及重複規則。重複鬧鐘使用規則作標籤，避免把過期日期當成未來日期。
- 原廠介面只到分鐘；拒絕已過期或已進入當前分鐘的單次提醒，避免送出後變成明天。確認視窗停留到過期時會重新驗證。
- 每日／每週的舊記事可計算下一次符合規則的時間；未來開始日期若會造成提早響鈴，則攔阻。每月或未知規則不會降級成單次鬧鐘。
- 同一來源已有送交紀錄，或同名、同時間與規則已有紀錄時，提示先核對、可能重複，仍由使用者決定是否重送。這是本機紀錄比對，無法發現原廠中所有重複鬧鐘。
- 只有開啟建立畫面後才寫入「待核對」。原廠取消不會回報，因此取消後仍可能有待核對紀錄；完成原廠儲存後，由使用者到連動紀錄確認。
- 修改或刪除 Junba 記事不會更新或刪除原廠舊鬧鐘。音效、音量、貪睡及勿擾行為請在原廠時鐘設定並實測。

## 自動驗證

使用 Java 17：

```bash
bash tools/test_native_alarm.sh
gradle --no-daemon --max-workers=2 --console=plain assembleDebug lintDebug
```

獨立的 Java 回歸檢查不依賴 Android 裝置或使用者資料，涵蓋分鐘精度、過期、跨日、每日／每週、星期對應、未來開始日、每月拒絕、夏令時間及確認視窗過期。這些檢查無法證明原廠時鐘接受 Intent 或實際響鈴。

## vivo V2413 / Android 16 待測

1. 先在現有版本備份並確認可還原；核對新舊 APK package、versionCode 與簽章。不得為安裝而自動卸載或清除資料。測試僅使用新建、無私人內容的提醒。
2. 建立兩分鐘後單次鬧鐘：確認預覽、原廠時間、標籤；完成儲存，鎖屏等待響鈴。到連動紀錄手動確認。
3. 測試每日與每週：核對原廠收到的重複日。週日應為週日，每日應有七天。
4. 同一記事再次送出應顯示已有紀錄提示；按取消或先開啟時鐘不應產生新的建立請求。
5. 修改記事時間後重送，應提示原廠舊鬧鐘仍需手動處理。到原廠取消建立後，Junba 不得顯示自動確認成功。
6. 測試過期、當前分鐘、較遠日期、未來開始的每日／每週及每月規則，應顯示原因且不送出。
7. 預覽開啟後等待時間過期，再按送出，應攔下或重新預覽，不得悄悄變成明天／下週。
8. 測試日曆不同提前時間（如 1、30、7200 分鐘），預覽應以活動時間減去所選提前時間計算，不能用活動開始時間代替。
9. 若沒有可處理的時鐘 App 或啟動被拒絕，顯示錯誤且不新增送交紀錄。

## 資料相容與回復

`native_links` 只新增可選的 `repeat` 字串欄位，沒有重新編號或清除舊資料；舊紀錄缺欄位時顯示「舊紀錄未記載」，不會自動重送。既有匯出會保留此欄位，舊程式可忽略它，無需破壞性遷移。既有同來源重送仍以最新請求更新該筆紀錄並改回待核對。

App 的套件、versionCode、簽章設定及記事格式維持既有值；debug APK 不是固定 release signing，不保證能覆蓋其他簽章的舊版。本次未執行任何卸載、清除資料、匯入或資料上傳。現有「匯入取代本機資料」缺陷仍待獨立修復；不要把它當作安全移轉工具。
